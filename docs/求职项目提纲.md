# 听见智能听书：求职项目提纲

适合投递 Java 后端实习，也可作为 Java + AI 应用工程方向的主项目。介绍重点是身份边界、助手接入、检索证据、受控问数与售后状态机。基础与新增实现的归属见 [来源与第三方说明](来源与第三方说明.md)，面试中应据实区分。

## 可据实改写的简历描述

**听见智能听书平台｜Java 后端与 AI 应用｜个人项目**

技术：Java 17、Spring Boot、MySQL、Redis、MongoDB、UniApp/Vue 3、Python FastAPI、模型工具调用、向量检索、BM25、SQL AST。

- 基于听书微服务源码接入 AI 助手，复用 Redis 登录身份，提供会员、收听进度、订单与售后查询；会话按认证用户隔离并持久化，工具禁止接收外部 userId，业务事实采用固定格式回复。
- 实现听友与独立管理员登录及 Java RBAC，普通用户无法审核，撤销角色立即生效；售后支持草稿、确认、审核、撤回及用户意见回显。
- 补齐本地下单、服务端价格快照、15 分钟订单关闭与 HMAC 支付回调；订单行锁和回执唯一约束处理并发重试，真实 MySQL 验证重复回调。退款使用数据库任务、30 秒租约、有限退避重试与独立渠道幂等凭据，覆盖响应丢失和实际订单服务重启。
- 实现售后申请状态机，以订单行锁统一并发转换，事务内保存申请与事件；确认校验归属、支付状态、金额快照及有效期，真实 MySQL 验证 6 次并发确认只生成一条确认事件。
- 实现听书提取式 RAG，按章节切分 12 份 Markdown 为 120 个片段，缓存真实模型向量，使用向量检索、BM25 与 RRF 融合召回；核验片段 ID 和逐字引用并提供原文来源，固定召回集 16/16 通过。
- 实现运营自然语言统计，使用 6 个聚合视图、指标目录、SQL AST 白名单、只读数据库账号及审计，限制单视图查询、最多 100 行和 3 秒执行时间，拒绝原始个人信息读取与写入。

投 Java 岗位时优先保留权限、支付退款和事务，再从 RAG 与问数中选择一条。投 AI 应用岗位时先写工具编排和 RAG。支付退款必须写“本地模拟渠道”；不要增加未经验证的 QPS、用户规模、正确率、性能提升或生产上线表述。

## 一分钟介绍

我在听书业务基础上实现了一个 Java 与 Python 协作的智能听书平台。Java 负责登录权限、订单、支付回调和售后事务，Python 助手负责选择查询工具；知识服务回答时展示原文依据，运营端用受控 SQL 查询聚合指标。我重点补了服务端身份隔离、MySQL 行锁与回调幂等，以及带租约的退款任务。用本地模拟渠道验证了响应丢失后的重试和真实服务重启恢复；前端能演示登录、播放、进度、订单、审核和退款状态。模型只有查询工具，不能代替用户或管理员执行交易；真实支付公司和付费音源尚未接入。

## 需要自己讲透的问题

1. **为什么不用模型直接查数据库？** 身份和 SQL 权限必须由服务端决定。个人工具不接受用户 ID；运营账号只能读聚合视图，AST 校验与数据库权限共同限制查询。
2. **为什么确认前还要再次校验？** 草稿创建到确认期间，订单支付状态或金额可能变化；确认时重新读取并锁定订单，核对快照和有效期。
3. **为什么先锁订单，再锁申请？** 草稿尚无申请行，订单行可作为同一订单的稳定串行点；所有转换采用一致锁顺序，避免并发产生多个活跃申请。还需理解数据库事务隔离和死锁重试。
4. **接口幂等如何实现？** 同一订单、相同原因的有效草稿复用；已 SUBMITTED 的同一申请再次确认直接返回现状；已 WITHDRAWN 的申请再次撤回同理。事件只在真正转换时写入，不能把它泛化为任意外部系统都实现了 exactly-once。
5. **网络超时怎么处理？** 服务器可能已提交，客户端按同一幂等键或申请编号重试、查询。申请与事件同一事务，审计失败整体回滚。退款渠道凭据独立提交，响应丢失时再次用同一退款编号查凭据，再确认本地业务；本次没有真实支付平台分布式事务。
6. **引用校验能保证什么？** 能保证片段存在、引用文字是资料原文；无法保证资料本身正确，也不等于自由生成回答的准确率。
7. **为什么小语料不用 Milvus？** 当前只有 120 个片段，SQLite 缓存与 NumPy 搜索便于本地复现；规模扩大后应基于实际延迟、内存和增量更新评估向量数据库。
8. **问数为什么不支持 JOIN？** 当前先验证有限业务口径和权限边界；允许更多 SQL 结构前需要补充指标目录、关联关系、资源限制与测试。
9. **管理权限怎么防绕过？** 普通账号与管理会话分离，角色与权限在 Java 数据库中校验，每次操作读取当前权限，撤销角色立即失效；审核员没有运营问数权限，页面隐藏按钮不是权限依据。
10. **哪些内容还没做？** 网关、生产身份治理和角色分配界面、密码找回/MFA、云点播、付费播放授权、真实资金支付退款、微信/App 真机。当前支付公司被本地渠道替代，不产生资金流水。
11. **为什么先读再锁仍可能重复回调？** MySQL REPEATABLE READ 的普通查询可能创建旧快照；订单锁等待后，回执查询必须采用当前读，不能继续使用旧快照。本次真实并发验收发现并修正了这一问题。
12. **数据库 outbox 与消息队列有什么区别？** 当前业务状态和任务同库同事务，工作进程轮询任务。它没有 MQ 的订阅和吞吐特性，但便于本地验证持久化与重试；不能把它称为 RabbitMQ 已接入。
13. **租约能保证 exactly-once 吗？** 不能。过期工作进程与新进程可能重复调用渠道，所以必须依赖稳定退款编号和渠道凭据幂等；业务回调锁与唯一回执处理重复确认。
14. **为什么退款失败不直接回滚审核？** 人工审核和渠道处理是两个事实。审核通过保持记录，REFUND_FAILED 表示渠道失败，管理员可以重试而不是重新审核。
15. **评测能说明什么？** 16 个固定召回场景验证书名、语义及拒答，20 个真实 Agent 场景验证工具与证据契约。样本有限、模型有随机性，不能宣称通用准确率或生产效果。
16. **如何定位一次跨服务失败？** 响应 x-request-id 沿 Python、Java、知识与问数链路传播；按同一编号查服务、路由、状态和耗时，再核验数据库事件。限流与超时只覆盖本地单实例 AI 请求。
